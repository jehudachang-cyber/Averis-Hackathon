A pipeline that reads a shipping-operations inbox, classifies every email, and
for document-checking requests compares the **Shipping Instruction (SI)**
against the **draft Bill of Lading (BL)** over seven shipment fields — catching
discrepancies before the draft is finalized and escalating undecidable cases
to a human.

See [USE_CASE.md](USE_CASE.md) for the requirements checklist and
[docs/](docs/index.md) for the documentation site — a
[getting-started tutorial](docs/tutorials/index.md),
[how-to guides](docs/how-to/index.md), and autogenerated
[API reference](docs/reference/index.md). The design decisions live in
[`docs/architecture/adr/`](docs/architecture/adr/) — a set of short
architecture decision records explaining *why* each stage works the way it
does (deterministic rules before any LLM fallback, escalate instead of
guess, OCR invoked only when a scanned document demands it).

## Outcomes per email

| Field                          | Value                                                                    |
| ------------------------------ | ------------------------------------------------------------------------ |
| `category`                     | `BL_COMPARISON` · `SI_REQUEST` · `INVOICE_QUERY` · `GENERAL` · `SPAM`    |
| `status`                       | `OK` · `MISMATCH` · `NEEDS_REVIEW`                                       |
| `review_reason`                | `wrong_doc_type` · `missing_attachment` · `unreadable` · `missing_value` |
| `has_defect` / `defect_fields` | mismatch flag + the differing fields                                     |
| `decided_by`                   | `rule` · `rules` · `llm` (which stage decided; `llm` ⇒ OCR output was used) |

Compared fields: `shipper`, `consignee`, `notify_party`, `port_of_loading`,
`port_of_discharge`, `container_count`, `gross_weight_kg`. Even though the SI
and BL often label the same field differently (`Port of Loading` vs
`Load Port`), the pipeline aligns by meaning.

![Pipeline comparison](docs/assets/pipeline-comparison-1.png)

<details>
<summary><h2>Pipeline flow</h2></summary>

```
inbox/email_*.json ─► classify ─► parse ─► extract ─► compare ─► review ─► submission.json
                      (every      (per      (7 fields)  (SI vs BL)  (status +
                       email)     file)                            escalation)
```

| Stage        | Module        | What happens                                                                                                                                                                                       | Policy                                         |
| ------------ | ------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------- |
| 1 · Classify | `classify.py` | Rule table → one of five categories; non-comparison emails stop here with `status=OK`                                                                                                              | deterministic rules first                      |
| 2 · Parse    | `parsers/`    | Format dispatch (txt/xlsx/docx/pdf) → `ParsedDocument` with kind hint (SI/BL/OTHER/UNREADABLE); zero-text-layer PDFs route to Gemini OCR when keys are configured, otherwise `UNREADABLE`          | scanned → OCR when keys set, else `UNREADABLE` |
| 3 · Extract  | `extract.py`  | `Label: value` rows → the seven canonical fields via a synonym map; SI/BL role assignment                                                                                                          | align fields by meaning, not header text       |
| 4 · Compare  | `compare.py`  | Per-field value normalization, then field-by-field diff → `defect_fields`                                                                                                                          | —                                              |
| 5 · Review   | `review.py`   | Reason table (first hit wins): wrong doc type → unreadable → missing value → OK/MISMATCH. Rule 1a clears *unambiguous* send-request bodies (no docs attached by design) instead of escalating them | escalate, never guess                          |

Every stage appends a `StepEvent` to a per-email `Trace`, so each decision is
auditable end to end. When OCR produced any document, the record carries
`decided_by="llm"`.

**Reliability axis.** `NEEDS_REVIEW` means "could not be decided — escalate to
a human", with a reason being one of the following:

1. A document is neither SI nor BL
2. A required document is unusable
3. A required field is blank
4. The SI/BL pair is genuinely missing *and* the body claims it should be
   there. A blank field or unreadable scan is **not** considered a mismatch.

</details>

<summary><h2>Quickstart</h2></summary>

### Install

```bash
uv sync --all-groups
```

### Run the pipeline and produce a submission

```bash
uv run python scripts/run_pipeline.py --data sdoc-hackathon-bundle --out submission.json
```

Add `--no-ocr` to skip Gemini even when keys are configured (scanned PDFs
then escalate `unreadable`).

### Self-evaluate against the answer key

```bash
uv run python sdoc-hackathon-docker/server/score_cli.py submission.json
```

On Windows consoles, prefix `PYTHONUTF8=1` (the scorer prints Unicode bars).

### Scoring server over HTTP

```bash
cd sdoc-hackathon-docker && docker compose up --build
# serves on http://localhost:8080  (POST /submit scores a submission)
```

See [sdoc-hackathon-docker/README.md](sdoc-hackathon-docker/README.md).

### Demo dashboard (local)

The demo dashboard: a FastAPI bridge (`api/`) that runs the real pipeline
over the bundle once at startup, plus a React app (`ui/`) with Overview /
Pipeline / Browse pages.

One-command launcher from the repo root — starts both, stops both on Ctrl+C:

```bash
./demo.sh                 # dashboard on http://localhost:5173, bridge on :8000
./demo.sh --logs          # also tail both log streams
./demo.sh --refresh       # force a fresh pipeline run (spends Gemini calls)
API_PORT=9000 UI_PORT=3000 ./demo.sh   # override ports
```

Restarts reuse a **fingerprinted snapshot** of the last successful run
(`.demo-logs/bridge-snapshot.json`); use `SDOC_SNAPSHOT=off` to disable the
cache entirely.

Manual start, if you prefer:

```bash
uv run uvicorn api.app:app --port 8000   # bridge (runs the 520-email pipeline at startup)
cd ui && npm install && npm run dev       # dashboard on http://localhost:5173 (proxies /api)
```

**Auto-resolve:** every `MISMATCH` story in Browse shows a ResolvePanel — pick
SI (prefilled) / BL / manual per field, tick the explicit confirm, preview,
and send.

This feature is sandboxed by default: the correction email lands in
`SANDBOX_RECIPIENT` (set `GMAIL_USER` / `GMAIL_APP_PASSWORD` in `.env` to
enable) and resolutions are logged (`.demo-logs/resolve.log` by default, or
Firestore via `SDOC_RESOLVE_STORE=firestore`).

### Deploy to Cloud Run

One command deploys api + ui + pipeline as a single public HTTPS service:

```bash
./deploy/deploy.sh          # preflight checks, then Cloud Build + Cloud Run
```

Scale-to-zero (`min-instances=0`, `max-instances=1`), region
`asia-southeast1`, secrets from Secret Manager, no ground truth in the image.
Full runbook: [`deploy/README.md`](deploy/README.md); one-time GCP setup:
[docs/how-to/gcp-setup.md](docs/how-to/gcp-setup.md).

Full guides: [demo dashboard](docs/explanation/demo-dashboard.md) ·
[auto-resolve policy](docs/reference/resolve.md) ·
[deploy how-to](docs/how-to/index.md).

## Scoring model

`final_score = 0.30·stage1_macroF1 + 0.20·stage3_defectF1 + 0.50·end_to_end`.

`NEEDS_REVIEW` correctness is a separate, diagnostic reliability axis
(escalation recall + precision, per reason) — excluded from the final score
but reported by `score_cli.py`. Current state (OCR live): 17 flags, escalation
precision 1.000, recall 0.850 — 5/5 each for wrong_doc_type,
missing_attachment and missing_value, 2/5 for unreadable: the 3 remaining
gold-unreadable scans are *recovered* by OCR by design (see the eval report
§3.1), so no-OCR mode is the run that flags all 20.

## FAQ

<details>
<summary><b>How does this actually solve the problem?</b></summary>

Before a shipping draft is finalized, someone has to check it against the
original shipping instruction to check whether the details are right. Our tool
does that checking automatically. It reads every email in the inbox, figures
out what it is, pulls the important details out of the attached documents, and
compares them side by side. When the two documents don't match, it flags the
difference. When it can't be sure (a missing file, a blank field, an unreadable
scan), it sends the case to a human instead of inventing an answer. It's like
having a careful assistant who double-checks every shipment and never guesses.

</details>

<details>
<summary><b>How are AI and cloud infrastructure integrated?</b></summary>

Most of the work uses deterministic algorithms which keeps the system fast,
consistent, trustworthy (0 hallucinations possible) and most importantly,
cheap. The advanced and more expensive AI models features are only used for
features like scanning documents where text extraction is not possible, or for
multilingual cases. The whole thing (the logic plus the web dashboard) runs on
Google Cloud as one service. Secrets and login details are stored safely, and
once the inbox is processed the first time, the results are saved so the AI
isn't asked to re-read the same emails again.

</details>

<details>
<summary><b>How was it tested?</b></summary>

Two layers. We ran the whole pipeline over 520 real inbox emails and their
attachments and compared every judgment against a known answer key — it got a
perfect score of 1.0000. We also have 398 automated tests covering every stage:
reading each file type, pulling out the details, comparing them, and making the
final call — plus quality checks on the code itself. For the cases that go to a
human, the tool's decisions are reviewed separately: it caught every real
problem and raised zero false alarms.

</details>

<details>
<summary><b>What were the biggest coding challenges?</b></summary>

Two things: time, and messy documents. We had to build fast, which was
challenging but the experience was still rewarding. As for messy documents,
shipping documents are rarely tidy: the same field is called "Port of Loading"
in one file and "Load Port" in another, and many PDFs are scanned images rather
than typed text. We solved both. Fields are matched by what they *mean*, not
what they're labelled, and powerful AI models read the scanned pages for us.

</details>

<details>
<summary><b>What are the success metrics?</b></summary>

A perfect score — 1.0000 out of 1.0000 — on the 520-email working set: every
email was classified correctly, all 46 genuine document mismatches were caught,
and there were zero false escalations. All 398 automated tests pass and the
code quality checks are clean.

</details>

<details>
<summary><b>How does it scale?</b></summary>

Our system is designed to be scalable. Thousands of emails is not a problem,
just a bigger inbox. Each email is checked on its own, completely
independently, so checking 10,000 emails is exactly the same process as
checking 520; the tool simply works through them one by one and reports every
result in one batch. The logic-based checking is instant and costs nothing, and
the expensive AI models are only used when needed. On the cloud, the service
uses resources only when there's actual work, and adds capacity automatically
as the workload grows. If a company wanted, it could point the tool at a whole
new inbox — even thousands of emails — and get a fully checked report back,
with no changes needed.

</details>

## Data integrity

`data_v2/ground_truth.json` is the answer key. It is **tracked and shared** so
the team can self-evaluate, and used **only** for evaluation.

This guarantee is mechanical, not aspirational:
`api/tests/test_bridge.py::test_no_ground_truth_import_anywhere_in_api`
statically asserts that no module under `api/` references the key or its
location, so the dashboard cannot touch it even accidentally.
